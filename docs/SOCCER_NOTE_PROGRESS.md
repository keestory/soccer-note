# Soccer Note 진행 기록

이 문서는 Kee Side-Hustle 아래의 Soccer Note 노션 허브에 동기화할 기획·디자인·개발·마케팅 기록이다. 노션 페이지 생성과 동기화는 상위 작업에서 담당한다. 저장소와 배포 대상은 `keestory/soccer-note` / Vercel `soccer-note`이며 다른 프로젝트와 섞지 않는다.

## 2026-11-02 — 쿼터 기록 저장 안정화

### 기획 결정

대상은 경기 직후 쿼터별 선수 배치·골·어시스트·클린시트·기여도·리뷰를 기록하는 아마추어 축구팀 감독과 코치다. 초기 `PROJECT_PLAN.md`의 오래된 체크박스보다 실제 구현과 최신 `DESIGN.md`, `UX-CONTRACT.md`를 기준으로 우선순위를 정했다.

기존 전체 저장은 현재 쿼터의 모든 기록을 먼저 삭제하고 새 행을 삽입했다. 삭제 이후 삽입이 실패하면 기존 기록을 잃을 수 있고, 저장 중 편집한 초안을 후속 재조회가 덮어쓸 수 있었다. 이번 릴리스는 이 경로를 먼저 개선한다.

S2 기존 기능 안정화. `discoverability: not-applicable` — 인증 뒤 기존 화면이다. `competitive_benchmark: not-applicable` — 코드로 확인한 보존 결함이며 경쟁 비교로 범위가 달라지지 않는다. `store_compliance: not-applicable` — 신규 개인정보·SDK·권한·결제·스토어 제출이 없다. 기존 미디어 작업의 동시 실행 제어만 변경한다. 데이터 쓰기·삭제 경계에 독립 보안 검토를 적용한다.

### 디자인 결정

- 기존 블랙/Volt 디자인과 단일 **전체 저장**을 유지한다. 호출되지 않는 개별 선수 저장은 새 기능으로 노출하지 않는다.
- 저장 전·진행 중·완료·실패를 지속적으로 안내한다. 실패 시 현재 화면의 입력을 유지하고 같은 저장을 재시도한다. 서버에 이미 반영됐는지 불확실한 신규 행을 잊지 않도록, 재시도 성공 또는 확인 후 화면 이탈까지 추가 편집을 잠근다.
- 저장 중에는 편집을 잠시 잠그고, 업로드·교체 기록 작업과 저장이 겹치지 않게 한다.
- 화면 이탈 시 저장되지 않은 초안을 안내한다. 이미 서버에 보낸 변경은 취소되지 않는다. 새 로컬 초안 저장은 추가하지 않는다.
- 8개 언어, 44px 이상 주요 조작 영역, 상태 알림과 키보드 접근을 검증한다.

### 개발 결정과 한계

기존 `(quarter_id, player_id)` 고유 제약으로 유지할 기록을 먼저 upsert하고, 응답을 확인한 뒤 이 편집기가 불러왔고 사용자가 제거한 ID만 삭제한다. 삭제는 쿼터와 ID 양쪽으로 제한한다. 응답 유실 후 재시도와 빈 명단을 검증한다. 저장 뒤 전체 편집기를 다시 불러오지 않고 서버가 확인한 ID를 반영한다.

여러 HTTP 요청으로 수행하므로 전체 작업을 하나의 트랜잭션으로 보장하지 않는다. 일부 변경이 이미 저장된 뒤 오류가 날 수 있으며, 안내 문구도 이 사실을 반영한다. 다른 기기의 동시 편집 충돌 해결과 새 DB 함수·RLS 마이그레이션은 이번 범위에 포함되지 않는다.

### 마케팅 준비

서비스 소개 초안: “경기가 끝나도 우리 팀의 기록은 남습니다. Soccer Note에서 쿼터별 포메이션과 선수의 골·어시스트·클린시트·기여도를 기록하고, 팀 랭킹과 선수 카드로 함께 돌아보세요.”

검증 후 사용할 릴리스 노트: “쿼터 기록 저장을 개선했습니다. 저장 중 상태를 분명하게 안내하고, 오류가 발생하면 작성 중인 내용을 유지한 채 다시 시도할 수 있습니다.”

외부 발송·유료 광고는 실행하지 않았다. 절대적 무손실, 완벽한 동시 편집, 스토어 승인이나 공개를 주장하지 않는다. 신규 분석 SDK나 개인정보 수집을 추가하지 않았다. 추후 동의한 사용자 관찰에서 저장 성공/재시도, 경기 기록 완료 시간, 재방문을 확인한다.

### 사용자 추가 방향과 디자인 비교

사용자 수가 적으므로 작은 표본의 비율·합성 테스트를 실제 성과로 해석하지 않는다. 의미 있는 실제 신호가 있으면 기능과 개선에 사용하며, 없으면 오류·화면·업무 마찰을 근거로 판단한다. 디자인 책임자는 비교 근거가 충분하면 정보구조부터 재설계할 수 있다. 매일 유저·사업·프로덕트 지표와 그래프를 노션에 누적하는 작업은 별도 데이터 담당이 맡으며, 이 작업에서는 중복 자동화를 만들지 않는다.

### 반론과 선택 기록

사용자의 세계 1위·월 $500M 방향은 장기적 포부이며 현재 실적이나 달성 약속이 아니다. 매일 이어지는 반복 실행은 상위 작업에서 관리한다. 논쟁의 양 대신 강한 반론, 고객 가치, 반복 사용·지불 의사의 실제 증거를 기록한다.

사업 모델도 검증 대상이다. 고객군·문제·과금·유통 변경을 뒷받침하는 근거가 나오면 유지안과 전환안, 작은 실험, 성공·중단 기준을 제안한다. 현재는 실제 규모·반복 사용·지불 의사 데이터가 없어 피벗을 단정할 근거가 없다. 제안 권한을 큰 사업 방향 변경의 실행 승인으로 해석하지 않는다.

### 후속 우선순위

1. **P0 권한 정책 확인:** 저장소의 기존 RLS 정책이 팀 가입 상태·제거 상태·편집 권한을 서버에서도 강제하는지 실제 대상 프로젝트에서 읽기 전용으로 확인한다. 소스상 광범위한 회원 접근/자기 가입 정책이 보이며 배포된 정책은 미검증이다. 이번 변경의 권한 경로는 기존 인증 클라이언트와 RLS를 유지한다.
2. **P0 서명 자산 관리:** Android 서명 설정/keystore 파일이 추적되는 것을 파일명으로 확인했다. 내용을 읽거나 출력하지 않았다. 노출 여부와 사용 중인 서명 체계를 확인하고, 회전·삭제는 별도 승인과 릴리스 연속성 계획 후 진행한다.
3. **P1 팀 전환 정합성:** 선택 팀을 바꾸는 동안 이전 팀 데이터가 남고 늦은 응답이 새 선택을 덮을 수 있다. 최신 요청만 반영하고 로딩·실패·재시도 및 팀 선택 시트 접근성을 정비한다.
4. **P1 경기 상태 통일:** 기존 `matches.status`와 날짜 기반 예정 판단이 화면별로 다르다. 경기 직후 당일 기록의 홈/랭킹/카드 의미를 통일하고 현지 날짜 기본값을 확인한다.
5. **P1 운영·검증:** 실제 OAuth, 역할별 RLS, 물리 iOS/Android 기기, 알림/미디어를 별도 검증한다. 웹 배포는 네이티브 artifact 또는 스토어 제출 증거가 아니다.
6. **P2 의존성과 측정:** 설치 시 기존 의존성 취약점 보고를 분리 검토하고, 사용자 관찰 결과로 다음 기능 우선순위를 정한다. 무조건적 major 업데이트는 하지 않는다.

## 2026-11-02 — 클라우드에서 팀 전환·계정 경계 재구성

사용자 지시에 따라 Mac을 재개하지 않고 별도 클라우드 `/workspace/soccer-note`에서 기존 PR #62를 이어갔다. Mac의 미커밋 변경을 복구했다고 주장하지 않는다. 다른 저장소·DB·RLS·권한·호스팅 환경변수는 변경하지 않았다.

팀을 고른 즉시 이름만 바꾸던 흐름을, 최신 성공 요청의 이름·기록·권한·캐시가 함께 확정되는 흐름으로 바꿨다. 실패·취소는 이전 팀을 유지하고 Sheet 안에 재시도/취소를 제공한다. 계정/팀을 떠난 저장 응답은 새 화면에 반영하지 않으며, 같은 팀 새로고침은 저장 초안을 지우지 않는다. 회원 연결만 실패한 경우 확인된 선수 ID로 연결만 재시도한다.

독립 디자인 비교는 360Player의 일관된 그룹 전환, TeamSnap의 직접적인 선수 추가, Spond의 그룹별 권한 문맥을 참고했다. 블랙/Volt는 유지하며 불필요한 확인 단계나 필수 입력을 추가하지 않았다. 독일어 320px 상태 문구 잘림을 발견해 수정했다.

## 2026-11-02 — 역할 별칭과 실제 협업 기록

무료·클라우드 전용으로 진행한다. 제품 코드·호스팅 설정을 변경하거나 운영 배포를 다시 실행하지 않는다. 기존 Supabase/롤백 접근 거부와 실제 지표 미확인 상태는 이번 문서 작업으로 해소됐다고 간주하지 않는다.
